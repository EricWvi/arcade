# 游玩记录与可视化

本文分两部分：

- **第一部分：已实现**。记录游玩时实际采集的数据，代码已上线。
- **第二部分：计划，尚未实现**。基于这些数据的可视化设想，目前还没有任何页面或接口。

## 第一部分：已实现的数据采集

### 一局怎么算

每次打开一个游戏页就算一局（play）。

- **生成 id**：游戏开始时，前端用 `crypto.randomUUID()` 为这一局生成 id。
- **上报时机**：开局、每 30 秒、页面隐藏、页面关闭（pagehide）、在站内离开游戏页时，都会调用 `PUT /api/plays/<id>`。
- **上报内容**：每次都是这一局到当前为止的累计值。
- **服务器的处理**：每项计数只保留较大值，所以上报丢失、重复或乱序都不会算错。同一个 id 只能属于同一个用户和同一个游戏。
- **刷新页面**：会产生新的一局。几局之间要不要合并，在展示时决定，见第二部分。

### 有效时长的定义

两个条件同时满足才计入有效时长：

- 页面可见（`document.visibilityState === "visible"`）；
- 最近 2 分钟内按过键盘，或在游戏区域内按下、移动过鼠标。

开局时视为刚刚操作过，所以片头动画等不需要操作的前 2 分钟也会计入。后台标签页的计时器可能延迟触发，单次计时间隔最多按 5 秒算，避免把一段长间隔整个计进去。

### 数据表 `plays`

每局一行，时间都是服务器时间的 Unix 毫秒。

| 字段 | 含义 |
| --- | --- |
| `id` | 这一局的 UUID，由前端生成 |
| `user_id` | 用户 |
| `game` | 游戏 key，即 games.yaml 里的键 |
| `started_at` | 服务器收到第一次上报的时间 |
| `ended_at` | 有效时长最后一次增长时的服务器时间。挂机或切到后台时不再推后 |
| `active_ms` | 有效时长，不超过开始至今的实际时间加 1 分钟余量 |
| `fullscreen_ms` | 有效时长中处于全屏的部分 |
| `keys` | 按键次数，按住不放产生的重复事件不计 |
| `clicks` | 在游戏区域内按下鼠标或触摸的次数 |
| `save_writes` | 成功上传存档变更的次数，大致反映进度推进 |
| `muted` | 最后一次上报时是否静音 |
| `timezone` | 浏览器的 IANA 时区，例如 `Asia/Shanghai` |
| `viewport` | 最后一次上报时的窗口尺寸，例如 `1440x900` |
| `user_agent` | 第一次上报时的浏览器 UA，最多 512 字节 |

查询"最近游玩"用的索引是 `(user_id, ended_at)`。

### 已有接口

- **`PUT /api/plays/<id>`**：上报一局的累计值。
- **`GET /api/plays/recent`**：返回最近玩过、且还在 games.yaml 里的 6 个游戏。除了游戏信息，还包括 `lastPlayedAt`（最近一局的 `ended_at`）和 `playedMs`（所有局的 `active_ms` 之和）。首页"最近游玩"用的就是这个接口。

### 已知局限

- **最后一次上报可能丢失**：离开页面时的上报靠 `fetch` 的 keepalive 发出，浏览器不保证一定送达。丢失时最多少记最后不到 30 秒。
- **按键数不够精确**：按键在整个游戏页上统计，不区分按键时焦点是否在游戏里。
- **存档写入次数会合并**：2 秒内的多次存档写入会合并成一次上传，只记一次。
- **几个字段只反映最后状态**：`muted` 和 `viewport` 只是最后一次上报时的值，不是整局的变化过程。

## 第二部分：可视化设想（计划，尚未实现）

> 以下内容都是计划，还没有对应的页面、接口或代码。实现时可能调整。

### 需要先补的能力

- **历史查询接口**：例如 `GET /api/plays?from=&to=&game=`，返回一个用户在某个时间范围内的原始记录，用来画图。目前只有"最近 6 个游戏"这一个汇总接口。
- **局的合并规则**：同一游戏相邻两局，如果前一局的 `ended_at` 与后一局的 `started_at` 间隔小于 5 分钟（暂定），展示时合并为一局，比如刷新页面或网络中断后重进。合并只在查询或前端计算时做，原始记录不改。
- **按本地时间统计**：按天、按小时统计时，使用每局记录的 `timezone` 换算成本地时间，不用服务器时区。

### 个人统计页的图表

| 图表 | 内容 | 用到的字段 |
| --- | --- | --- |
| 游玩日历 | 类似 GitHub 贡献图，每格一天，颜色深浅表示当天的有效时长 | `started_at`、`active_ms`、`timezone` |
| 时段热力图 | 7×24 网格，显示一周中哪些时段玩得最多 | `started_at`、`active_ms`、`timezone` |
| 游戏时长排行 | 各游戏累计有效时长的横向条形图 | `game`、`active_ms` |
| 单局时长分布 | 直方图，看是短时间随手玩多，还是长时间沉浸多 | 合并后的 `active_ms` |
| 投入度 | 每分钟按键加点击次数，区分动作游戏和休闲游戏 | `keys`、`clicks`、`active_ms` |
| 进度曲线 | 某个游戏随累计时长增长的存档写入次数，近似看进度推进 | `save_writes`、`active_ms` |
| 设备与习惯 | 全屏占比、静音占比、电脑与手机占比 | `fullscreen_ms`、`muted`、`viewport`、`user_agent` |

### 游戏详情页上的小组件

- 游戏页标题旁显示"上次游玩时间 · 累计时长"。
- "我的记录"折叠面板：最近几局的时间线，每局显示开始时间、时长，以及是否推进了存档。

### 以后可能值得补采的数据

目前没有采集，需要时再评估。

- **按分钟的活跃度**：目前只有整局的总数，看不出一局之中什么时候最投入。
- **游戏内进度**：例如 Hot Air 的已解锁关卡数、星星数。需要按游戏写解析存档的适配器，比如从 SharedObject 中读取 `levelsopened`。
- **进入方式**：从首页的最近游玩、分类货架、游戏页的"更多游戏"还是直接访问进入，用来看哪些入口最常用。
